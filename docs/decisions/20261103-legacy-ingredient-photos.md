# 舊食材照片的裝置端保留

2026-11-03，接續 #14／PR #24。使用者在實機更新被舊內嵌照片擋下後，明確選擇保留照片。

## 決定與邊界

僅在該裝置主動執行一次性食材更新時，將既有 `photoUrl`／`photo` 的內嵌圖片解碼為 Blob，保存於同來源 IndexedDB `fk_ingredient_photos` 的 `photos` store。以圖片 MIME 與內容 SHA-256 為識別，寫入完成後重新讀回並核對內容，才允許食材更新。

這是既有私人照片的本機格式遷移，不是新增相片上傳的替代方案。新增照片原有上傳／失敗規則不變。不傳送到 GitHub、Supabase 或另一個 Scope；官方食材 JSON 與 Personal Kitchen State 均不新增照片欄位。

食材及備份 JSON 只保存 `localPhotoRefs`；照片欄位保存 `null` 或原本的遠端 URL。顯示時才由二進位圖片建立臨時 Blob URL，該 URL 不得持久保存。Base64 不再複製至任何新 JSON／localStorage 備份。既有含 Base64 的原件在使用者執行更新前保留，啟動合併不重寫它。

## 備份與失敗處理

先完成所有二進位照片備份及讀回驗證，再建立既有一次性更新的 pending journal。含舊照片的 `before`／`original` 改為原營養與中繼資料加上照片參照，不宣稱與舊 Base64 JSON 逐位元組相同；圖片內容須逐位元組相同。無舊照片的備份仍保留原始字串。

照片寫入／讀回／格式核對失敗：原兩個食材 key 不動。食材交易失敗或頁面中斷：還原舊營養與照片參照，不把 Base64 寫回 JSON。已完成的二進位備份不自動刪除；暫存資料清理仍須另外同意。備份期間若原件被其他分頁改動，停止更新，不覆寫較新的資料。

裝置完成轉換後，舊版程式不認識照片參照，直接回退到 PR #24 會讓照片暫時無法顯示（圖片內容仍在 IndexedDB）。因此程式回復須保留本次照片讀寫相容層，再回退其他變更；資料回復使用備份中繼資料與二進位圖片，不重新寫入 Base64。不可把單純 Git revert 說成完整資料回復。

一般重新載入及食材編輯保留參照並顯示原照片；新遠端照片取代顯示值時不讓舊本機參照蓋回。localhost 寫檔不輸出裝置照片參照或 Blob URL。

## 相容性與驗證

無照片、遠端照片 URL、既有無照片完成標記均維持原流程；未完成的舊裝置可重試同一個更新入口。IndexedDB 不可用、配額不足、照片缺失或內容不同時明確停止，不默默丟照片。裝置清除網站資料仍會失去本機資料；本次沒有建立跨裝置或雲端照片備份。

須驗證二進位內容、雙 key／custom-only、舊 `photo` 欄位、重開後顯示、編輯後保留、各階段失敗、頁面中斷、並行改動、無新 Base64／Blob URL 寫入，以及兩個 Scope 完全不變。真實 iPhone 驗收另列，不能以桌面瀏覽器代替。
